## 实际业务链路

`complete_delivery_flow_preserves_history_and_snapshots` 在内存核心执行完整链路，`complete_delivery_flow_is_persisted_in_sqlite` 使用同一流程经真实 SQLite 适配执行：

1. 创建成员、产品、项目、迭代；原始需求转正式需求并评审批准。
2. 建立需求版本关联、开发任务，开发提交待验收，测试角色验收关闭；开发自行关闭被拒绝。
3. 固定测试用例版本和构建，执行失败并转 Bug，确认、修复并提交修复构建，测试角色处理复测关闭；开发自行关闭被拒绝。
4. 对修复构建重新建立测试单并执行通过，完成产品验收，按构建、测试单、需求和修复 Bug 的范围发布。
5. 发布后修改需求，新内容进入变更状态；旧发布和任务不能将新版标为已交付，历史发布快照不变。
6. 关闭数据库连接并重新打开，同一状态的对象、版本、关系、操作日志和发布快照一致。
7. 从该业务状态创建一致性备份，恢复到新目录，再次核对完整状态和发布快照一致。

Bug 目前通过测试角色状态流转表达复测结果，独立的复测构建、结论和附件交接记录尚待完善，不能将这份测试作为全部复测业务已完成的证据。

## 存储证据和失败边界

本地适配创建 `workspace.json`、`data.sqlite` 和 `attachments/`。SQLite 中分别保存工作空间、带筛选索引的业务对象、内容版本、审计和原始操作；附件按内容 SHA-256 分目录去重。附件使用项目已有的 `tempfile` 安全临时文件能力，落位前刷新文件，原子落位后刷新目录，避免自行实现随机临时名和清理协议。

| 场景 | 已执行的结果 |
| --- | --- |
| 两个连接依次修改 | 第二个连接读取到最新状态；旧对象版本返回冲突，不覆盖已保存内容 |
| 两个线程同时提交相同基础版本 | 恰好一个成功，另一个返回明确版本冲突 |
| 同一操作重试及重开后重试 | 返回原回执，对象、审计和修订号不重复增加；载荷不同则冲突 |
| 日志 INSERT 被数据库触发器拒绝 | 业务投影、版本、审计和修订号全部回滚；同一上传操作可在解除失败条件后重试 |
| 附件文件先落位而数据库失败 | 不产生可见的虚假附件；不可变文件可供原操作重试复用 |
| 伪造附件元信息或缺失文件 | 命令失败，批量中的其他业务修改也回滚 |
| 附件重复上传 | 不同业务引用共享一个内容文件，各自保留元信息和审计 |
| 附件删除或业务归档 | 读取遵守墓碑；历史所需文件保留，恢复后仍可核对 |
| 附件目录不可用、文件损坏或缺失 | 返回错误，不能把失败当成保存成功 |
| 数据库投影被直接改写 | 重新打开时重放日志并比对，拒绝不一致的工作空间 |
| 写入仍有 WAL 的数据库进行备份 | 使用 SQLite 备份 API，恢复后评论、墓碑、业务与附件字节一致 |
| 备份缺少文件、哈希不符或含越界路径 | 拒绝恢复，不留下半成品目标目录，也不替换现有工作空间 |
| 通过符号链接替换数据库或附件路径 | Unix 平台测试拒绝相关读取或恢复 |
| 通过归档隐藏失败测试、未结束任务或 Bug | 业务核心拒绝；发布停止维护后也不能改写范围或正文 |
