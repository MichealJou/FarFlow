## 真实浏览器操作

使用 Codex 内置浏览器，通过 Vite 同源代理连接独立的 FarFlow HTTP 进程和新建的临时 PostgreSQL 集群。未使用现有公司的数据库，也未向公司的禅道写入内容。验收账号和运行配置仅保存在本机运行环境，不写入本记录。

1. 所有者登录，创建“FarFlow 首版验收”空间及产品、项目。
2. 界面创建需求 `71ff4be1`，保存描述、验收标准、指派，提交评审并批准 V1。
3. 上传 `验收证据.txt`，评论中提及成员并引用该附件。退出后从另一会话重开，评论与附件仍在；通过界面下载后的 SHA-256 与原文件一致：`f8b59c0accaced14a14d615b4d4a7da4caf28440905b1ca94ca62ee96aad1951`。
4. 管理员创建测试账号，在成员页绑定“测试”角色。新账号实际登录后被要求修改临时密码，改密成功后重新登录。
5. 开发任务 `7beb1282` 关联需求 V1，开始开发、提交待验收；独立测试账号验收关闭。测试账号没有用户管理入口。
6. 测试账号创建并评审用例 `d8268be1`。所有者创建就绪构建 `51225070`；测试单 `0cc38cb0` 固定用例 V1，执行表单实际展示固定步骤。
7. 在独立环境明确填写“流程演练”的失败结果，从执行 `7d64b50b` 创建 Bug `4d4806cb`。该数据不代表对产品真实缺陷的判定。
8. 所有者创建独立修复构建 `921650c7` 并提交解决方案，Bug 进入“待复测”；测试账号在回归测试单 `4b393712` 单独保存通过执行 `2ac25db5`，结束测试单，再选择该新执行记录完成独立复测。Bug 变为“已关闭”。
9. 所有者对当前需求 V1 产品验收；创建演练发布 `c4dffd11`，选择需求、已复测 Bug、修复构建及回归测试单，提交待发布并确认发布。界面显示固化的五项发布快照。
10. 需求进入变更，修改描述后形成 V2，重新提交评审。评论与附件保留；再次打开已发布版本，快照中的需求仍是 V1。
11. 实际逐项切换十二套配色，读取页面选中值与 CSS 主题色一致，最后恢复浅灰钴蓝。另检查 390 × 844 窄窗口，导航与新建表单可操作。

上述 Bug 和发布均为显式标注的流程演练数据。证明的是 FarFlow 界面到真实后端的业务动作与保存链路，不是已经完成桌面版、Git 协作、生产性能或正式发布。
