## 实际断言

- 不同对象和不同评论合并后均存在；优先级与负责人等独立元信息能够合并，已有正文不丢失。
- 相同正文修改可归并为同一内容版本，但两个原始操作继续保留。两个不同内容修订不能自动混成一个数字版本。
- 同一字段不同值的双方均进入问题集合，基础状态保留，电脑时间再大也不能取得覆盖权。
- 六种三副本导入顺序得到相同完整投影，包括对象、版本、审计、回执和问题集合。
- 原始操作和决策都支持幂等重试；处于冲突的操作重试返回冲突，不制造成功回执或新增记录。
- 冲突决策必须由启用的所有者或项目经理执行。经理不能通过替代命令越权添加所有者。
- 明确不采纳时，原始提案和决策仍在操作图中，基础业务状态保持不变，不伪造一次业务修改。
- 并发决策再次形成问题；旧分支后续操作不因另一条并发决策被自动放行。
- 删除评论与并发回复保留双方冲突；停用成员与其离线写入不会静默选择一方。
- 三个所有者同时各自停用时，完整重放仍保留至少一位有效所有者，并报告业务约束问题。
- 同一用例的并发通过和失败均保留为冲突；不同用例的测试结果可独立合并，双向导入结果一致。
- 严重 Bug 与发布并发时，发布保持待发布；明确采纳该 Bug 后，正常发布门禁继续阻止发布。
- `complete_delivery_flow_replays_from_git_operations` 使用同一业务辅助流程执行需求收集、评审、任务、失败测试转 Bug、修复复测、验收、发布和后续改版，再从序列化操作集合重建，状态一致。

## 观察范围

本轮的“双副本”和“三副本”是操作集合副本，尚未通过真实 Git 仓库传输。已验证内存缓存不进入序列化，129 条线性操作的缓存结果与冷重放一致；这不是 1 万工作项、5 万操作的性能验收。

仓库文件落位、真实附件同步、SQLite 索引重建、Git 提交和远端同步、文件包、异常退出恢复、同步中心 UI 和三模式迁移仍待实现，不能把本记录视为完整 Git 模式可用的证据。具体协议及下一层要求见 [Git 操作协议](../06-Git操作协议.md)，整体范围仍以 [交付进度](../05-交付进度.md) 为准。
