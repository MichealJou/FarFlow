## 七项 Git 专项

位于 `crates/core/tests/git_transfer.rs`，直接使用实际 SQLite 索引、系统 Git、真实文件包和临时裸远端，没有模拟 Git 调用。

1. `git_source_propagates_freeze_and_member_confirmations_before_local_handoff`：两个真实数据仓库通过裸远端同步，所有者和开发者在不同设备确认，查看者不计入也不能确认。冻结后业务、普通复制和未确认导出被拒绝。正式包在本地暂存，完整核心文本与原空间相等，原始请求回执可重试，字节一致。错误角色、回执和早于确认的完成时间拒绝且不污染阶段。合法完成后本地接续；远端克隆及恢复文件包仍保留只读完成状态。Unix 私有备份目录与恢复文件权限实际检查为 `0700`／`0600`，完成前公开记录不含源令牌。
2. `private_backup_restores_only_the_frozen_source_and_failed_completion_never_publishes_a_phase`：普通公开包克隆保持冻结且不具备发起控制。私有令牌损坏时无法完成，公开阶段仍正常。把原目录移离运行路径后，用私有备份恢复原设备，重新确认并正式交给本地。重复恢复同冻结计划保留确认记录，不能以旧备份覆盖已经完成的源；错误格式和非所有者在创建目标前被拒绝。
3. `late_offline_business_is_retained_and_requires_cancel_merge_and_a_new_cutpoint`：未收到冻结的旧副本继续产生业务，直接上传先返回非快进；正常同步保留双方业务和冻结记录。确认、导出及首次完成均拒绝迟到切点。原发起副本取消并同步后可以继续，合并所有业务再建立新计划。旧计划与已有确认记录 ID 都不能重用。
4. `parallel_freezes_remain_readable_but_cannot_complete_until_each_origin_cancels`：两个离线副本各自冻结，合并后保留两个计划，普通业务仍只读，状态单值查询报冲突但列表及业务读取可用。不允许自动选胜、继续确认或跨设备取消。两个发起设备分别取消并同步后可正常写入，再创建新共同计划。
5. `invalid_git_prepare_paths_roles_and_tampered_public_records_never_open_writes`：错误角色、模式、ID、时间、占用备份路径不产生冻结。私有备份或文件包指向源仓库内部、或经符号链接指回源内部时，在写入前拒绝，不留下额外文件。私有控制目录被文件占用时，即使备份已经保存，源也不发布半次冻结且可继续业务。公开记录被改为空设备、漏确认成员、引用自身或未知前序、错误文件名后，读取和冷启动均拒绝；恢复原记录后正常。
6. `completed_git_sources_keep_late_bytes_read_only_and_reexport_only_the_original_cut`：源完成、目标激活后，旧副本继续上传附件。迟到字节保留在只读源及恢复包中，目标没有被自动写入。原凭据仍可取得，重导正式包与原切点完整文本相等；不能取消或在源继续写业务。
7. `late_ownership_changes_do_not_strand_frozen_control_or_restore_business_permissions`：迟到分支把开发者提升为所有者并停用原所有者，复现原实现无法读取或取消冻结的问题。修复后，原切点所有者仅可读取控制并在发起设备取消旧计划，普通业务读取和写入仍被拒绝；新所有者继续业务并创建新计划，新计划只要求新启用可写成员确认，旧停用成员不能查看新计划。

第七项先实际失败，错误为原所有者已停用；修复控制权限后专项通过，再重新执行完整回归。没有用恢复旧用户的业务角色来绕过问题。

## Git → 服务实际账户与数据库

`migration::git_source_hands_original_history_to_real_service_accounts_after_member_confirmation` 使用临时 PostgreSQL、真实密码和会话、实际 HTTP 路由请求及正式迁移库接口：

- 由已有复制历史建立 Git 源，原始历史身份不同于目标服务账户 ID。
- 未确认不能导出；合法所有者确认后，服务按完整一一映射只读暂存，查看者不能代替所有者。
- Git 源完成后，只有映射后的所有者可以激活；状态、来源、负零及原始文本一致，原请求可以幂等重试，原附件可读。
- 服务通过真实会话继续评论，Git 源仍只读；完整服务备份恢复保留全部状态。

## 独立服务进程与完整发布链路

扩展 `workspaces::full_delivery_runs_through_service_roles_and_replays_from_postgres_after_reconnect`。保留原需求、任务、测试失败、Bug 修复、独立复测、验收和发布全部流程，以及重启、日志重放、备份恢复和既有交接。

已由服务正式交给 Git 并继续评论的完整发布空间，随后在 Git 再次冻结。先验证旧目标计划 ID 不能重用、旧目标激活凭据不能覆盖当前源阶段；全体可写成员确认后，按原 ID 暂存到正在运行的另一个服务。真实 TCP HTTP 可见暂存，Git 提交完成凭据后服务激活，所有核心文本逐字段相等；通过独立进程的真实 HTTP 继续评论并读取实际附件，发布快照不变。

同一完整测试继续验证服务 → 本地，停止实际服务进程后本地仍可续写、读取附件、备份和恢复。管理动作调用真实 Rust 库，服务业务走独立进程与 TCP HTTP，本地业务直接访问 SQLite；这些证据没有被当成桌面点击验收。

## 自查与实际边界

没有新增第三方依赖。新源控制复用已有历史校验、私有临时目录、原子文件、目录同步、系统 Git、文件包、索引和导入恢复；提取原文件包实现供普通导出及私有备份共用。业务引擎及模型、服务生产代码和 SQL 没有改动。

成员明确声明本人所有副本已同步停写，不代表软件远程锁定了未知设备。已知迟到或并行计划阻止首次完成；完成后的迟到数据保留供人工核定，不自动写入目标。私有恢复前必须确认原发起副本离线、没有另一处相反最终决定。普通 Git 模式仍以可信成员和仓库文件权限为边界，不能承诺集中登录撤权或无服务全局一致性。

测试只使用自建临时数据库、临时 Git 仓库和回环端点，没有修改公司禅道、已有业务库或外部仓库。迁移 CLI、桌面 UI、性能、旧格式升级、安装包和最终禅道比对继续按[交付矩阵](../05-交付进度.md)推进，默认浅灰钴蓝及可切换主题已经确认，界面仍待实现。协议见[Git 源交接](../18-Git源交接与冻结确认.md)。
