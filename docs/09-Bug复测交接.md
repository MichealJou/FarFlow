# Bug 复测交接

共享核心使用独立的 `ResolveBug` 和 `RetestBug`。提交解决进入 `resolved`，不等于关闭；通用 `Transition` 不能直接将 Bug 关闭。当前实现适用于本地、Git 与未来的服务适配，界面尚待接入。

## 正常流程

提交 Bug → 确认 → 修复中 → 提交解决 → 测试复测 → 通过关闭。复测失败重新激活，阻塞保留待复测。已关闭对象可带说明重新激活。

| 动作 | 权限和校验 | 保存结果 |
| --- | --- | --- |
| 提交解决 | 开发或项目负责人；Bug 已确认；必须提供处理依据 | 解决方案、操作者、时间、操作 ID、内容版本、修复构建或重复对象 |
| 修复复测 | 测试或项目负责人；选择提交解决时的同产品就绪构建；必须写实际结论 | 构建、执行证据、结果、说明和原解决记录快照 |
| 非修复确认 | 测试或项目负责人核对重复、原设计等处理依据 | 保留方案及依据，不伪造修复构建和测试执行 |
| 失败或重开 | 必须有说明 | 清除当前解决字段，增加重开次数；过去复测记录不丢失 |

所有者遵循共享核心的管理权限规则，可以执行这些动作；本地单人工作空间不强制要求另一名自然人。开发角色本身没有关闭权限。

## 执行证据

手工提交的 Bug 可以按复现步骤直接复测，必须明确实际构建和说明，可关联测试执行。由失败或阻塞的测试执行产生的 Bug 必须使用原用例在修复构建上的回归执行，不允许删除原始来源以绕过检查。

关联执行必须在提交解决之后单独保存，与复测的构建、产品和结果一致，并且是该测试单和用例的最新结果。旧通过记录、其他用例记录、其他构建和再次解决前的执行都不能冒充本轮复测。

每次复测追加 `retest_records`，包含操作、成员、时间、内容版本、方案、解决记录快照、构建、执行、结果和说明。字段不能通过普通创建或编辑伪造。相同请求重试幂等，旧对象版本返回冲突，失败校验不留下半次状态变化。评论和附件继续使用对象的统一协作能力。

已解决或已关闭 Bug 的复现内容发生变更前，应先重新激活；修改负责人或优先级等元信息不要求重开。当前复测固定到提交解决时选择的构建，没有实现“之后任意构建自动证明包含修复”的提交祖先推断。

## Git 并发与验证边界

复测和优先级等独立元信息可合并。同一 Bug 的相反复测结论形成冲突，保留双方原始操作，由有权成员核对后明确决策；不得按时间选一方。

完整业务流程已在内存、SQLite、Git 操作图与真实仓库执行，并经过备份、文件包和真实本机远端恢复。上述属于后端证据；真实桌面交接、附件预览和服务账户操作尚未验证。当前项目仍处于开发阶段，先前试验版通用关闭操作的升级迁移尚未验证，不声明历史试验仓库兼容。见 [最新验证](验证记录/2026-10-25-远端同步与标准复测.md)。
