# Git 源交接与冻结确认

Git 源已接入正式交接库接口，可转本地或服务，保留同一空间 ID、业务 ID、原始请求、完整业务图、来源和实际附件。结合已有方向，三种模式间六条不同模式的正式交接方向均有实现；本地／Git 桌面向导已接入，服务远端向导、完整桌面产品其他边界及部署验收仍待完成。

## 正常流程

1. 所有协作者先同步、处理业务冲突，盘点本人使用中的副本。
2. 所有者在一个指定发起副本准备迁移，选择本地或服务目标，保存私有恢复备份后发布冻结记录。
3. 同步冻结记录。所有启用的可写成员分别核对相同历史切点，明确确认本人所有副本已同步并停止写入，再同步确认记录。
4. 发起副本取得全部确认，检查没有迟到业务或并行冻结计划，再导出正式包。
5. 目标按原空间 ID 只读暂存并返回核对回执；服务目标另要求完整历史身份 → 真实账户映射。
6. 发起副本中具备冻结切点所有者权限的成员核对回执并确认源完成，目标所有者用专用凭据激活目标。
7. 同步源完成记录，原 Git 副本保持业务只读。目标继续工作，已发布快照不被交接后的评论改写。

只有来源历史中的启用可写成员需要确认，包括所有者、项目管理、产品、开发和测试角色。查看者和停用成员不计入确认集合。集合从冻结切点重建，不能通过修改界面名单省略成员。

成员确认是一项明确声明：本人名下全部副本已同步并停写。记录保存成员、实际提交确认的设备、时间和说明；这不等于软件已经远程锁住每一台物理设备。Git 模式没有集中在线锁，未登记、未同步的旧副本必须由团队盘点，不能承诺对它们即时停写或撤权。

## 库接口

| 接口 | 行为 |
| --- | --- |
| `GitWorkspace::source_transfers(actor)` | 成员读取全部源计划，包括阶段、发起设备、必须确认的成员、确认设备集合和是否出现迟到业务；不包含待发令牌 |
| `prepare_transfer(actor, id, at, target, backup_destination)` | 当前所有者准备新计划，保存私有恢复包，再发布固定切点的冻结记录；相同发起副本及未结束计划可重试 |
| `acknowledge_transfer(actor, at, id, note)` | 当前可写成员核对切点，明确声明所有本人副本已同步停写；拒绝空说明、错误时间、无关成员、迟到业务和已知并行计划 |
| `export_transfer(actor, destination)` | 所有者在全部确认且切点一致后导出正式包；完成后重导出仍只取原切点 |
| `complete_transfer(actor, at, receipt)` | 仅发起副本首次确认源完成；先校验全体确认、回执、私有控制、时间和拟追加记录，再发布完成凭据 |
| `cancel_transfer(actor, at, id)` | 仅发起副本取消尚未完成的指定计划；全部未完成计划都已取消并同步后，副本恢复写入 |
| `restore_transfer(private_backup, destination, actor)` | 所有者核对私有恢复包并恢复原发起设备与控制；目标存在时只接受同一冻结计划，不覆盖不同空间或已完成计划 |
| 已有 `transfer_status(actor)` | 一个有效源计划时返回其阶段；已知并行计划返回冲突，完整列表通过 `source_transfers` 查看 |

源计划的导出、完成与取消权限按该冻结切点的启用所有者核对。读取源计划时，当前启用成员可以查看；仍有效计划的历史切点所有者也可以查看迁移控制。这样，迟到分支即使交接角色并停用了原所有者，发起副本仍能由原切点所有者取消冻结；普通业务读取和写入仍按当前成员状态拒绝原停用用户。取消并创建新计划后，旧用户不再获得新计划的读取资格。该例外仅作用于迁移控制，不恢复业务权限，也不改变服务模式的真实账户鉴权。

这些 Rust 管理接口已接入[统一正式迁移 CLI](23-正式迁移命令行.md)，真实进程覆盖成员停写确认、私有发起副本恢复及交接；本地／Git 桌面迁移向导已接入并完成原生连续往返，服务远端向导仍待完成。业务的真实 HTTP 验证、管理命令行和桌面数据接续分别记录。

## 追加记录与业务屏障

原 `workspace.json` 保持不可变。新增 `transfers/前缀/记录ID.json`：冻结记录保存计划、发起设备、历史取消计划集合和必须确认的成员；确认记录保存实际设备、成员、时间及说明；结束记录保存取消或完成状态，只有已完成记录包含该计划的完成凭据。

记录的成员权限、原切点、模式、时间、前序关系和完成凭据均从完整历史核对。拟新增记录在写入之前先在内存中与已有记录一起验证；错误完成时间、缺失确认或不合法结束记录不会先落盘再报错。

冻结中的源拒绝保存业务、附件上传、冲突决策和普通复制导出。提交、获取、上传及文件包传输仍允许，用于传播冻结、确认和取消，不能把同步成功当成业务已经解冻。目标处于暂存阶段时，原有传输限制继续生效。

来源记录纳入 Git 文件树白名单、不可变历史检查、导入恢复计划和索引指纹。合并使用既有私有暂存及恢复流程，先验证完整文件集合，再逐步安装；缺依赖、改写或删除已提交记录、非法路径、符号链接及内容不符时拒绝接收。旧版本不识别新记录路径，会拒绝打开或接收相应数据，需要协作者升级后再开始迁移。

新建交接目录、私有控制和接收后的交接分类目录分别调用已有目录同步能力，普通文件仍按既有原子写入和同步方式保存。恢复校验、重开及失败路径通过软件测试验证；不把这些测试称为物理断电实测。

Git 目标激活后若又成为下一次迁移的源，重试上次目标激活不会覆盖当前源阶段。旧计划 ID 也不能用于新计划。

## 迟到业务

冻结后收到来自旧离线副本的新业务，传输仍保留原始操作和字节，并将该源计划标记为存在迟到业务；不会丢弃新文件来强行满足旧切点。此时不能再确认、导出或首次完成该计划。发起副本需取消，所有副本同步取消和业务、解决冲突后，以新 ID 重新备份和冻结。

若交接已经完成后才收到旧副本业务，源仍保持业务只读，迟到内容留在源历史及恢复文件包供核定，不能自动写入已激活目标。原完成凭据可以重取，正式包重导出只提取原切点，目标既有状态和发布快照不因此改变。团队须核定迟到内容并在目标补充必要业务，不能在源重新开启旧计划。

## 并行计划

不同离线副本可能各自准备迁移。同步后保留全部计划及业务，界面可以读取完整列表；不自动选择一个，也不允许继续确认、导出或完成已知并行计划。每个发起副本分别取消自己的未完成计划并同步，全部取消后才恢复写入，再创建一个新的共同计划。

取消和首次完成限于同一发起设备，配合同机锁避免正常客户端在不同副本分别作出相反最终决定。私有备份恢复会恢复该设备身份，所以恢复前必须确认原实例离线、没有另一处已经取消或完成；不能同时运行原副本及恢复副本。文件所有者手工复制私有控制或在未知离线副本作出相反决定，不属于可自动裁决的在线一致性保证。

## 私有备份与恢复

准备阶段的备份目录包含：

| 文件 | 内容及边界 |
| --- | --- |
| `workspace.farflowpack` | 完整原业务、Git 祖先和新冻结记录；单独创建副本仍是只读，没有待发令牌 |
| `recovery.json` | 与包内冻结记录一致的私有控制及专用令牌；仅用于所有者恢复发起副本，不上传 Git |

备份在私有临时目录完成并核对后落位，源再安装私有控制并发布冻结记录。Unix 备份目录为 `0700`、恢复文件为 `0600`。未完成令牌只存在私有恢复文件及 `.git/farflow/source-transfers`，不进入公开记录、普通数据包或远端。

私有备份和普通文件包的输出位置必须在源 Git 数据仓库之外；指向源内部的符号链接路径也会在写入前拒绝，防止在规范数据目录中留下额外文件或私有恢复资料。

备份写入失败不会发布源冻结。若备份已保存而本机私有控制安装失败，当前源仍未冻结；查询当前阶段后修复，不把备份自动当成另一个并行源。若最终发布后返回存储错误，先重新读取阶段并幂等重试，不能依据一次错误响应自动作出相反决定。

正常恢复保留冻结，需重新收齐备份后尚未保存的确认；不会直接恢复为可写。完成后的公共恢复文件包保留完成阶段，所有合法副本仍只读，合法所有者可重取原完成凭据。令牌绑定单个计划，SHA-256 用于完整性，不构成来源系统的数字签名；本机文件和可信团队边界与既有 Git 模式一致。
