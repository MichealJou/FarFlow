# Git 操作协议与当前实现

本协议用于同一套业务核心在离线副本之间交换操作。操作图与语义合并位于 `crates/core/src/gitlog.rs`，仓库文件、离线文件包与索引恢复已接入 `repository.rs`，见 [仓库存储与离线交换](07-Git仓库存储与离线交换.md)。[远端网络同步](08-Git远端同步.md)已接入，同步中心、原文比较和明确决策界面已接入，见 [桌面 Git 同步](22-桌面Git同步.md)。

## 数据真源与身份

`GitLog` 包含初始工作空间和不可变操作集合。初始工作空间必须与 `State::new` 生成的有效单所有者状态完全相同，不允许在初始状态里夹带业务数据或历史。两个副本只有初始状态完全相同才可合并。

| 操作字段 | 含义与校验 |
| --- | --- |
| `schema` | 当前为 1，其他格式版本拒绝处理 |
| `workspace_id` | 必须属于同一个工作空间 |
| `id` | 成熟 UUID 实现生成，必须与内部业务操作或决策 ID 一致 |
| `device_id` | 当前副本设备身份，不是用户账户或权限凭据 |
| `parents` | 创建操作时已知的全部操作头，明确因果依赖 |
| `change` | 原始业务请求或明确的冲突决策 |

操作图中的依赖必须存在且不能循环。同一操作 ID 的规范化业务内容不同，合并整体失败，不能覆盖已有记录。请求、命令和业务载荷中的未知字段被拒绝，避免新含义被旧程序静默丢弃。命令中的 UUID、状态和权限仍由共享业务核心校验。

设备计数从父操作的因果信息计算，不使用电脑时间判断先后。不同离线副本必须有独立设备身份；重复使用同一设备身份分叉会被识别。后续仓库适配负责在新副本生成并保存本机身份，该身份和本机缓存不得提交到业务仓库。

## 合并与重放

每条原始操作首先在自己的因果上下文中验证。对于并发操作，分别通过同一个 `State::execute` 验证两种执行顺序，再比较业务状态、固定内容版本和各测试用例的最新执行结果。只有两种顺序都合法且结果等价，才允许自动合并。

比较时不会把最后更新时间或审计排列差异当成业务覆盖依据；原始操作、作者和时间仍保留。测试执行的全局排列号用于规范投影，同一用例的最新结果仍单独比较，不能因忽略排列号而误合并通过与失败。

| 并发场景 | 当前行为 |
| --- | --- |
| 创建不同对象、各自评论 | 均保留，导入顺序不改变规范投影 |
| 同一对象修改优先级、负责人等独立元信息 | 两种顺序通过业务校验且结果相同时自动合并 |
| 内容修改与不影响内容版本的元信息修改 | 经同一校验允许合并 |
| 同一字段修改为不同值 | 双方进入冲突，不按时间选择一方 |
| 两个不同正文修订，即使分别改标题和正文 | 保留两份原始提案并要求决策，避免把同一个数字版本对应到不同内容 |
| 两份相同正文修订 | 业务结果及内容版本一致时可合并，两个原始操作仍保留 |
| 删除评论与并发回复 | 保留双方提案进入冲突，不生成悬空回复 |
| 同一用例的并发执行结果 | 进入冲突，不能随机选择最新结果 |
| 不同用例的并发执行 | 可独立合并，结果固定到各自用例版本 |
| 停用成员与其离线写入 | 进入冲突，由有权限的人明确处理 |
| 严重 Bug 与同构建发布 | 发布与缺陷提案进入冲突，版本不被直接发布 |

成对比较不能代替完整业务校验。规范重放仍执行所有共享规则，例如三个所有者同时各自停用时，不能因为任意两条都合法就允许工作空间失去所有者。不能执行的操作作为约束问题保留，原始载荷不丢失。

`GitView` 同时返回规范业务状态、问题集合和生效回执。问题区分并发冲突、依赖阻塞和业务约束失败。带问题的状态是尚待处理的投影，不代表三模式迁移或发布已通过。当前公开写接口在问题未处理完前暂停新业务写入；更细的对象范围交互仍待界面集成。

## 明确决策

决策有自己的操作 ID、操作者、时间、被处理的操作集合、处理说明和可选的替代业务命令。只有启用的所有者或项目经理可以处理同步冲突，替代命令仍要通过正常角色权限和业务校验，不能借决策提升权限。

两个冲突提案不会在规范投影里自动挑选一方。保留某一方或合并双方内容时，提交明确的替代业务命令；选择不采纳则可不附命令，保留基础状态，并将选择记录在操作图中。原始提案不被改写或删除。

决策只确认操作者实际见过并明确引用的问题。旧分支的后续操作必须保留为阻塞，不能借另一个并发决策自动放行。两个副本对同一问题分别作决策时，决策本身再次进入冲突，直到有新的明确处理。

## 缓存与重建

当前使用标准库 `OnceLock` 复用已验证的内存投影。缓存不序列化，外部操作集合变化后失效；正常因果追加直接复用当前投影，序列化重开则从不可变操作重建。已有 129 条线性操作的缓存与冷重放一致性测试，但没有据此宣称万级数据性能达标。

SQLite 派生索引已接入并通过删除、损坏及恢复测试；它只能是可重建数据，不能成为第二份可独立写入的主库。原始业务请求的指纹保持不变；规范投影因合并调整对象修订号时，也不能篡改原请求。

## 下一层仓库适配的交付条件

以下保留完整 Git 模式的交付条件。第 1 至 4 项及第 5、6 项中的本机仓库、离线交换、真实 HTTP/TCP、凭据助手及远端竞争已有验证；取消、超时、同步中心和冲突决策已接入；SSH、HTTPS 托管登录及其他界面部分继续实现。证据见 [真实仓库验证](验证记录/2026-10-25-Git仓库与离线交换.md)及[最新验证](验证记录/2026-10-25-远端同步与标准复测.md)。

1. 工作空间清单和按操作 ID 分文件的不可变记录；附件按实际字节哈希落位并校验，冲突提案引用的附件也不能遗漏。
2. 先持久保存完整操作，再更新本机 SQLite 索引；索引失败应明确表示“本机已保存、索引待恢复”，重开能重建。
3. 多文件导入在本机锁下校验和落位；保留持久恢复记录，异常退出后能继续完成或明确失败，不能向界面返回半包成功。
4. 新副本生成独立设备身份，普通运行不提交本机路径、数据库、同步游标和凭据。
5. 使用成熟 Git 命令完成提交、离线交换、获取和上传；固定参数，不执行数据仓库中的钩子，不默认强推。
6. 双真实仓库的同步、断连重试、远端更新、损坏文件包、缺失依赖、附件去重及索引删除后重建。
7. 同步中心显示问题、原文与明确决策；本地保存、Git 提交、远端收到分别显示真实结果。

上述条件属于完整 Git 模式的原定范围，不能用操作图已通过单测来替代。
