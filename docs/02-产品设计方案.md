# FarFlow 产品设计方案

产品名确定为 FarFlow 研流，定位为从需求收集到版本发布的研发协作工具。用户可以先在本地管理工作，再通过 Git 异步协作，或连接集中服务开展团队协作；三种模式使用相同的核心业务和客户端。

## 已确认的范围

- 同一套代码支持本地、Git、服务三种模式，初始化时选择。
- 完整考虑禅道的业务关系，重点提供需求、研发任务、Bug、测试和发布闭环。
- 支持多人通过 Git 或文件交换，也支持服务端集中协作。
- 数据可导出、可备份、可迁移，优先使用可免费自托管的组件。
- 当前共享核心、本地、Git 及 Rust + Axum + PostgreSQL 服务端已有实现；完整界面仍待完成。用户已确定默认浅灰钴蓝，并要求其他配色可切换。

## 三种模式

| 能力 | 本地模式 | Git 模式 | 服务模式 |
| --- | --- | --- | --- |
| 使用方式 | 打开本机工作空间 | 打开本地仓库副本 | 连接服务地址和工作空间 |
| 业务数据 | 本地 SQLite | 仓库中的结构化操作文件 | 服务端 PostgreSQL |
| 查询 | SQLite | 本机 SQLite 索引 | 服务端查询 |
| 协作 | 文件交接 | 拉取、合并、推送，或交换数据包 | 集中保存，在线协作 |
| 离线操作 | 完整支持 | 完整支持，稍后同步 | 首版保留未提交草稿，离线浏览缓存可后续增加 |
| 身份 | 本地个人身份 | 成员和设备身份，加 Git 凭据 | 服务端账户和成员权限 |
| 权限能力 | 本机访问边界 | 可信团队协作规则；仓库读取权限决定数据可见性 | 服务端强制权限和数据范围 |
| 消息 | 本地待办和提醒 | 同步后获取协作变化 | 在线通知和站内待办 |
| 应用服务 | 无需 | 无需；可复用已有 Git 托管 | 需要可选服务端 |

三种模式不是收费等级。实时性、身份可信程度和细粒度权限受协作方式影响，不强求做出虚假的完全一致。

## 初始化与工作空间

首次打开显示“创建或打开工作空间”，提供三个并列选项。安装本身不要求注册账号，模式保存在工作空间配置中，不是全局不可更改的安装选项。

| 模式 | 初始化信息 | 检查 | 成功结果 |
| --- | --- | --- | --- |
| 本地 | 名称、目录、个人身份 | 目录可写、空间足够、不是其他工作空间 | 创建本地数据文件和附件目录 |
| Git | 新建仓库或连接仓库、目录、成员身份、可选远端 | Git 可用、仓库可访问、格式版本兼容 | 建立仓库副本、重建本机索引 |
| 服务 | 服务地址、登录方式、选择工作空间 | 服务兼容、账户有效、访问权限 | 保存连接配置及安全凭据引用 |

侧栏固定显示工作空间名称和模式。Git 模式展示“本机已保存、待提交、待上传、最后同步、待解决冲突”；服务模式展示连接状态和未提交草稿。切换工作空间前提示处理当前草稿。

同一工作空间的模式变更通过迁移向导完成，先备份、预检、导入目标，再核对。不能只修改一个模式字段后继续使用不匹配的数据。

## 核心流程

1. 提出人在收集箱记录业务问题，产品人员澄清并转成正式需求。
2. 需求写明验收标准，通过评审后进入产品计划。
3. 项目关联产品，迭代选择本次需求并拆分任务。
4. 开发完成任务，关联提交和构建，交给测试或验收人。
5. 测试针对构建执行具体版本用例；失败时创建 Bug 并保留测试来源。
6. 开发提交修复，测试复测；失败重开，通过关闭。
7. 产品负责人确认需求验收，发布负责人核定交付范围。
8. 发布保存版本、构建、需求、修复、已知问题及结论快照，后续反馈回到收集箱。

任务可以独立于需求创建，Bug 可以独立于用例提交，但需要标明原因和所属范围，避免强制虚构关联。

Bug 的处理、复测及重开采用独立动作，实际规则见 [复测交接](09-Bug复测交接.md)。通过、失败和阻塞均保留记录；非代码修复方案确认的是处理依据，不显示为已完成代码修复测试。

## 状态和校验

| 对象 | 主流程 | 分支及约束 |
| --- | --- | --- |
| 收集项 | 待整理 → 待澄清 → 已受理 → 已转化 | 可重复、拒绝、归档，均保留原因 |
| 需求 | 草稿 → 评审中 → 已批准 → 已关闭 | 驳回回草稿，批准后实质修改进入变更；实现阶段另行展示 |
| 任务 | 待处理 → 进行中 → 待验收 → 已关闭 | 暂停、取消、退回、重开；提交完成不等于已验收 |
| Bug | 待确认 → 待修复 → 修复中 → 待复测 → 已关闭 | 重复、无法重现等另有处理结论，复测失败重新打开 |
| 测试执行 | 待执行 → 执行中 → 已完成 | 结果为通过、失败、阻塞、未执行或按约定跳过，不只一个布尔值 |
| 发布 | 草稿 → 待发布 → 已发布 → 停止维护 | 测试阻塞需处理或明确例外；发布范围存在未解决冲突时禁止发布 |

需求实现阶段根据关联任务、测试、验收和发布事实计算，详情展示阶段来源。产品验收和发布由明确动作完成。工时不是强制完成率来源，零工时和无工时应能正常表达。

需求正文和验收标准变更需要新版本；任务、用例、测试及发布分别记录依赖的版本或快照。所有状态动作通过业务命令校验，直接拖动看板也不能绕过规则。

## 信息架构与页面

主导航建议为：工作台、收集箱、产品、项目、任务、测试、Bug、发布、文档。成员、存储、同步、备份和集成放入工作空间设置。项目集、DevOps、治理和 AI 在功能启用后呈现。

核心列表采用“范围导航 + 表格或看板 + 详情面板”。筛选支持保存为个人视图；跨页面返回保留筛选、排序和位置。

| 页面 | 主要内容 |
| --- | --- |
| 工作台 | 当前需处理事项、关注的产品和项目、模式与同步状态 |
| 需求详情 | 内容和验收标准、版本、评审、关联任务、测试、Bug、发布、动态 |
| 任务详情 | 工作内容、负责人、状态、关联需求版本、提交和构建、完成及验收记录 |
| Bug 详情 | 复现、环境、附件、影响版本、修复版本、解决方案、复测和动态 |
| 发布详情 | 版本说明、固定交付范围、测试结论、已知问题、产物引用和实际交付记录 |
| 同步中心 | 本机变化、接收变化、冲突对比、合并结果、上传状态和错误恢复 |

列表默认展示常用字段，按需展开高级字段。详情中的历史与关联始终可见；不会用一排同名“状态”让用户猜测开发、测试和发布分别到哪里。

## 成员和权限

基础角色为所有者、产品负责人、项目负责人、开发、测试和只读成员。角色可兼任，工作空间成员身份与 Git 提交作者分别记录。

服务模式对读取、修改、指派、状态操作、发布、导出和附件下载分别校验工作空间和数据范围。管理员权限不自动等于每个产品的业务批准权限。

Git 模式面向拥有仓库副本的可信团队。成员规则可以约束正常客户端的操作，但不能阻止仓库持有者直接读取或修改文件，也不能即时撤销离线副本。需要严格数据隔离时使用服务模式，并将不同可见范围拆成不同工作空间或仓库。

本地模式使用设备和文件访问边界；协作者身份可在导入时保留，不要求运行统一账号服务。

## 统计口径

| 指标 | 定义 |
| --- | --- |
| 开发待办 | 当前范围中处于待处理或进行中的研发任务，暂停另列 |
| 待验收任务 | 已提交完成、尚未验收关闭的任务 |
| 待修复 Bug | 已确认但尚未提交有效处理结论的 Bug，按严重度分组 |
| 待复测 Bug | 已提交处理结论、尚未复测关闭的 Bug |
| 已修复 Bug | 解决方案为代码修复的记录，区别于重复、拒绝和无法重现 |
| 用例覆盖 | 在指定需求集合中，具有有效关联用例的需求数除以需求总数；空分母显示无数据 |
| 测试通过 | 所选测试范围最新有效执行结果中，通过、失败、阻塞、未执行分别展示 |
| 发布完成 | 已发布版本及其固定范围，不由任务进度百分比推断 |

每个报表显示范围、过滤条件和数据时间。Git 模式另显示同步时间和未解决冲突数量，不能把本机已知数据当成团队实时全量数据。
